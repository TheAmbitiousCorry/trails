# Adapters

Trails is agent-neutral. The server speaks MCP for agents and HTTP for hooks and the browser, and no code path depends on which runtime is calling. Everything specific to a runtime lives in `adapters/<runtime>/` and consists of placing text and configuration, never of code the server needs.

## What the server offers every runtime

- The MCP endpoint at `/mcp`, stateless Streamable HTTP, session identified by argument, see [mcp](./mcp.md).
- The protocol in the `session_start` response: a short how-to-walk block and the tag vocabulary, so an agent that was given only the MCP entry still learns the protocol on first contact.
- Project endpoints, `POST /api/projects {repo, runtime_session_id?}` and `GET /api/projects`, see [storage](./storage.md#registry): a hook registers its repo with the server, and the server never creates `.trail/id` for it. When the body carries `runtime_session_id` the server remembers in memory which project it belongs to, so a `session_start` with only that id is placed in that project.
- Four hook endpoints under `/api`, all plain JSON over HTTP so a shell script with `curl` can call them, at `TRAILS_URL` when set, else `http://` plus `TRAILS_ADDR`, else `http://127.0.0.1:` plus `TRAILS_PORT` when set, else `http://` plus the first field of `$HOME/.trail/server` when the pid in it is alive, else `http://127.0.0.1:7777`, see [storage](./storage.md#address). The repo is `CLAUDE_PROJECT_DIR` when set, else the `cwd` field of the hook payload, else the hook's working directory, the same for all five scripts. The project is the id in the nearest `.trail/id` at or above the repo. Each body below also carries `project`, that id, when the scripts found one:
  - `POST /api/pre-read {project, runtime_session_id, path}`: asked before a native read. Finds the live entries whose file, range or dir anchor covers the path (as `edited` does) and replies `{decision, entry_id, read_when, entries, total}`. `entries` lists every such entry as `{entry_id, read_when}`, ordered by id and capped at eight; `total` is how many there are, and `entry_id` and `read_when` repeat the first of them. `checked` when one exists and the session has an `ok` `read` event, at any depth, on at least one of them; `turned_back` when one exists and the session has read none of them, with `entries` carrying the whole list; the agent may read any one of them to clear the gate. `unstarted`, with the same fields, when no open session matches the runtime id and the body's `project` holds a live entry that anchors the path, and records nothing because there is no session to record on; `unmapped`, with no entry fields, when none anchors the path. Each call records one `off_trail` event with the repo-relative path as target and the decision as result, see [trail](./trail.md#events); a repeated `turned_back` on the same path in the same session records nothing new. When no session matches it replies `unstarted` for an anchored path in the named project, else `unmapped`, and records nothing.
  - `POST /api/off-trail {project, runtime_session_id, path}`: for runtimes with only an after-read event. Records an `off_trail` event with result `ok` and replies `{entry_id, read_when}` for the anchored entry when one exists, or `{}`. A runtime whose shell tool bypasses the read gate records those reads through this endpoint without denying them.
  - `POST /api/edited {project, runtime_session_id, path}`: records an `edit` event with the path as its target and replies `{entries: [{entry_id, read_when}]}` for every live entry with a file, range or dir anchor whose path is the edited path or a directory containing it, or `{entries: []}`. When no session matches, it is dropped and replies `{entries: []}`.
  - `POST /api/stop-check {project, runtime_session_id}`: replies `{open: bool, session_id, task, blocks: n, gaps: [{id, query}], edits: [{id, path}]}`, `session_id` and `task` naming the open session so an agent that lost its id can call `session_end`, `edits` listing the entries [trail](./trail.md#edited-entries) holds the session open for, and increments `blocks` on each call while the session is open. The hook blocks while the reply says `open`; on the third call the server closes the session with `ended_by: forced` and replies `open: false, forced: true`. When several open sessions share a runtime id the most recently started wins.
  - Hooks know the runtime's own session id, not the Trails one, so `session_start` accepts an optional `runtime_session_id`, and all four hook endpoints resolve the open Trails session by it. A body with `project` is served by that project alone, so a repo's hook can never reach another repo's session; a `project` the server does not hold is refused `404 project_unknown`. A body without `project` (a runtime that cannot run the scripts from inside the repo, or a repo with no `.trail/id`) looks for the runtime id in every project's open sessions, the most recently started winning, and the server remembers in memory which project answered for an id and asks it first while it still holds an open session for that id. A session-start hook prints the project id and the runtime id into the agent's context so it can pass both along. When no session matches, pre-read replies `unstarted` for an anchored path in the named project, else `unmapped`, off-trail and edited are dropped and stop-check replies `open: false`. A hook body's `path` may be absolute: the server relativises it against whichever of the project's bound checkouts contains it, primary first, see [storage](./storage.md#registry).
- Fallbacks when a runtime has no hooks: the sweep closes a session with no call for four hours with `ended_by: timeout`, its gaps show in the browser's gap queue, and off-trail reads and edits are simply not recorded and no read is turned back, and no edit gate holds the session open.

## Autostart

The session-start hook acts only when `.trail/id` exists at or above the repo; a directory with no id at or above it and none one or two levels below it (hidden directories, `node_modules` and `vendor` skipped) has not opted in, and the hook contacts no server, starts nothing and prints only `Trails: this repo has no .trail/id; run trails register to put it on the trail` as its context text, after the binary line when that applies. A directory with no id of its own but repos below it, such as the parent of several checkouts, has the hook register each of them with the same body and print `Trails projects under this directory: <id> (<path relative to the directory>), ...` in place of the single project line; a registration answered `409` adds the server's `fix` as its own `Trails: <fix>` line. Otherwise it registers the repo by `POST /api/projects {repo, runtime_session_id}` (`runtime_session_id` only when the runtime supplies one) at the hook's address with a one-second cap, `repo` being the directory that holds `.trail/id`. When nothing answers, it runs `$TRAILS_BIN` (default `trails` on `PATH`) with `serve --addr <addr>`, no repo, detached, with output appended to `~/.trail/server.log`, retries the registration for up to three seconds, and the one server then holds this repo beside every project it already knew. When the binary is missing it starts nothing. With a server already up the whole check is the one registration `curl`.

The hook then prints, in order and each only when it applies: the binary line; `Trails project: <id>`; and `Trails runtime_session_id: <id>`. The agent passes `runtime_session_id` to `session_start`, and `project` where its MCP entry is not the shim. The binary line is printed on every run, with a server up or not and with or without an id in the repo, whenever `trails` (or `$TRAILS_BIN`) is not found: `Trails: the trails binary is not on PATH; the MCP entry runs trails mcp, see adapters/README.md`. There is no port line: the shim entry carries no port.

## Opening the browser

Every adapter tells its agent to run `trails open trail` when the user asks to see the trail, `trails open map` or `trails open graph` for those pages, and to report the URL printed. Claude Code ships this as the user-invocable skill `trail` (`/trail`); the other runtimes carry a `Seeing the trail` section after the protocol text in their instructions file, which `scripts/check-adapters.sh` excludes from the protocol comparison. The command is the one described in [storage](./storage.md).

## What an adapter contains

1. The protocol text from `protocol/PROTOCOL.md`, formatted for where that runtime reads project instructions.
2. The MCP server entry for that runtime's configuration, pointing at the machine's server (port 7777 by default). The Claude Code plugin entry is the stdio shim `trails mcp` (`{"command": "trails", "args": ["mcp"]}`, no port in it), which the runtime starts in the project directory with `CLAUDE_PROJECT_DIR` set. The shim relays each JSON-RPC message to the one server's `/mcp` and sends the id in the nearest `.trail/id` as `X-Trails-Project`. When no `.trail/id` is at or above the directory, it looks one and two levels below it (hidden directories, `node_modules` and `vendor` skipped, as the session-start hook does) and sends the one id it finds, with that repo as the project root; with none or several found it sends no id and the server's own rule applies. So `session_start` needs no `project` there, see [mcp](./mcp.md); it finds the server's address by the rule in [storage](./storage.md#address), so a machine on another port sets `TRAILS_PORT` once in the `env` block of `~/.claude/settings.json`, which moves the server, the hooks and the CLI with it. The HTTP endpoint stays the path for scripts and for runtimes without stdio: their entries point at the machine's server (port 7777 by default), pass `project` when the server holds several projects, and, where the config cannot read an environment variable, edit the URL by hand to match the port.
3. The `Seeing the trail` section (Claude Code: the `trail` skill).
4. Hook wiring that calls the five shared shell scripts in `adapters/generic/hooks/` (they source `trails-common.sh`) on that runtime's events, when it has them: `trails-session-start.sh` at session start, `trails-pre-read.sh` before a file read, `trails-off-trail.sh` after a file read where there is no before-read event, `trails-edited.sh` after a file edit and `trails-stop.sh` at stop. `trails-pre-read.sh` denies the read in the runtime's deny form when the server says `turned_back`, with the reason `Trails has an entry for this file: <id>, <read_when>. Read it with read(<id>) first, then open the file.`, and when it says `unstarted`, with the reason `Trails: this repo has a map and an entry for this file (<id>, <read_when>). Start with session_start(task, project: <project id>) and read(<id>) before opening it.`, the project id being the one the hook resolved from `.trail/id`; it prints nothing on `checked` or `unmapped`, and with the server unreachable it passes the read through. A runtime with only an after-read event gets the off-trail signpost instead, and its README says the gate there is a signpost, not a turn-back. A runtime with no after-file-edit event says so in its README and has no edit gate. The Stop gate and `session_end` are unchanged by the read gate. A runtime whose subagents share the parent's session id gives each its own runtime id by appending the agent id, and gets a start hook (`trails-subagent-start.sh`) and a stop hook of its own. `adapters/HOOKS.md` holds the verified event names and shapes per runtime.

`protocol/PROTOCOL.md` is the single source of the protocol text. Adapter copies are verbatim copies of it and `scripts/check-adapters.sh`, run by `make test`, fails when a copy drifts.
