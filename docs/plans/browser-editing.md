# Editing entries from the browser

## Goal

A person reading an entry in the browser can edit it in place (title, `read_when`, Markdown body, tags, anchors, `requires`, `see_also`, and `decided_by` and `decided_at` for a decision) and, separately, confirm it. Editing and vouching are two acts: a save keeps the entry's tier and never clears staleness, and Confirm runs the existing human confirm (`trail.ConfirmHuman`), which re-checks the anchors and makes the entry verified. A save goes through `entries.Write` as actor `user` ([entries: write rules](../context/core/entries.md#write-rules)), never overwrites a change the editor did not see, and shows any refusal's rule and fix in the form. Governing pages: [web_ui](../context/core/web_ui.md), [entries](../context/core/entries.md), [principles](../context/core/principles.md) rule 7.

## Decisions

- **One write path, explicit human deltas.** `POST /api/p/<id>/entries/<id>` calls `entries.Write` with `Actor: "user"` and a new `Edit: true` flag. These are named changes to the shared write path, each with its own test:
  - **Tier kept.** An `Edit` update stores the entry's current tier (and `tier_before_stale`) instead of setting verified.
  - **Anchor hashes kept.** An `Edit` update keeps the stored hash and `ok` of every anchor whose type, path and range are unchanged; only new or changed anchors are resolved. A stale entry stays stale until Confirm.
  - **Anchor rule.** An `Edit` that leaves the anchor set unchanged skips the anchor rule (the per-kind requirement and resolution), so an entry whose commit anchor is no longer reachable, or the anchorless root summary, can still have its wording edited; it stays stale until Confirm.
  - **Duplicate rule.** An `Edit` that leaves title, `read_when` and first paragraph unchanged skips the duplicate rule. Otherwise a duplicate refusal offers replace or distinct (merge is refused on updates, `rules.go:263`).
- **Confirm is its own route.** `POST /api/p/<id>/entries/<id>/confirm` calls `trail.ConfirmHuman`; a stale anchor refuses it with the anchor named.
- **Concurrency token.** `GET /entries/<id>` returns `etag`, built from `updated_at`; the save sends it; `WriteRequest.IfMatch` is compared inside the write transaction (which already holds the write lock, `store.go:48` `_txlock=immediate`); a mismatch is refused `stale_edit`, answered 409 with the current entry, and the form keeps the draft beside the newer text. Every writer of an entry must touch `updated_at` (checked in step 2). The MCP leaves `IfMatch` empty, which skips the check.
- **Staged entries.** The browser has no checkout, so a save to a staged entry is refused `staged_elsewhere` naming the branch, and the Edit button is hidden there. This changes `write.go:135`, which today exempts the browser. An original with a staged copy may be edited; the form says the copy will then come back as a `conflicts_with` pair at promotion.
- **Refusals.** The edit route keeps the browser's existing refusal shape (400, `rule: fix`, as `SignPage.vue` parses), plus 409 for `stale_edit`. No second shape.
- **Audit.** One `logUserEvent` helper writes the `user` event for every browser write: sign, supersede, promote, edit and confirm.
- **Pinned.** `stale_edit` joins `entries.RefusalRules`, which the golden test pins.

## Non-goals

- Creating entries from the browser; editing kind or sign.
- Authentication. The Host and Origin guard refuses cross-site browsers but not a local process that sends no Origin, so a local agent could call the browser routes and write as `user`. Principle 7's "an agent never overwrites a verified entry" holds through the MCP; the spec says so.
- A rich-text editor: a Markdown textarea with the existing renderer as preview.

## Unknowns

- **What the write rules do to a human no-op save on real data.** Step 1 measures it before anything is built.
- **`fanOut` on a human update of a lone verified summary** may count the entry itself (`rules.go` fanOut). Step 1's replay shows it.
