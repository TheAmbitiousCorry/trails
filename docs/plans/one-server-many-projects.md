# One server, many projects

## Goal

One Trails process on a machine serves every project that has opted in, and each agent session and each browser tab works inside one project. Today [storage](../context/core/storage.md) says one process serves one repo and one database, which forced one port per repo (`.trail/port`, added today) and one process per repo. The target: `trails serve` holds a registry of projects, each with its own `~/.trail/<id>/trail.db` and repo path; an MCP session names its project once at `session_start` and every later call is scoped by its session id; the hook endpoints find the project through the runtime session id; the browser lists projects at `/` and keeps every existing page under `/p/<id>/`. The per-repo port file goes away.

## Non-goals

- Authentication or any multi-user story. Still loopback only, one person per machine.
- Cross-project search, links or signs. A session sees one project.
- Changing the per-project database layout or migrations.
- The Supersede action on the entry page. It lands first as its own one-sentence change, outside this plan.

## Unknowns

- Whether the official Go MCP SDK lets one handler serve all tools while a request's project is chosen per call. Resolved before step 1: yes. `NewStreamableHTTPHandler`'s getServer callback sees only the `*http.Request`, before the body is parsed, so it cannot pick a project; but tools are registered once and each typed handler receives its input, so the project is resolved inside `trail.Record` from `session_id` (or `project` for `session_start`). `Recorder.DB` and the `Checker` are bound to one store today, so both move behind the resolved project.
- How much of `server/internal/web` assumes a single `*store.Store` in package scope. Step 3 reads it first.

## Steps

1. [x] **Registry and MCP scoping (walking skeleton).** New package `server/internal/project`: a `Project` value that owns everything per-project (the `*store.Store`, the `Recorder`, the anchor `Checker`, the sweep loop) and a mutex-guarded `Registry` with `Open(repo)`, `ByID`, `BySession` (an open session id, by asking each project's `sessions` table, cached in memory and rebuilt on demand so a restart loses nothing), `ByRuntime` and `List`. `Open` reads `.trail/id` and refuses a repo without one (the id is created only by the CLI, see step 2), opens `~/.trail/<id>/trail.db`, applies `.trail/map.md` and writes `~/.trail/<id>/repo`. Two checkouts with the same id (clone, worktree): the later `Open` wins the `repo` file and `Project.Repo`, with a log line; the `Checker` reads `Repo` at call time. Nothing is registered per project: MCP tools are registered once, and `trail.Record` takes a `trail.Resolver` that the `Registry` implements (`project` imports `trail`, so `trail` cannot name the registry), resolves the project once from the call (`session_id`, or `project` for `session_start`) and hands the handler a `*Project`; no handler calls the registry itself. An `unknown_session` refusal (no project holds the id) is returned unlogged, since there is no database to log in. On start the server opens every `~/.trail/<id>/` whose `repo` file names a directory that exists, plus each `--repo` flag (repeatable); with no `--repo` flag `serve` still uses the working directory, until step 2 removes that default. `session_start` gains `project` (the id from `.trail/id`); it may be omitted only when the registry holds one project, else refused with `project_unknown` naming the ids held. Every other tool resolves the project from `session_id`, refusing `closed_session` as now. The sweep runs per project. Until steps 2 and 3, the existing `/api` hook routes and the web routes resolve the sole project and answer 409 `project_ambiguous` when the registry holds more than one, so `make test` stays green after this step. Spec: storage.md (process layout, registry, the `repo` file, same-id rule), mcp.md (`session_start` argument and refusals). Verification: `go test ./...` with a test that starts one server over two temp repos, starts a session in each, writes in both, and reads back only its own; a `look` with the other project's session id does not see it; a restart over the same home finds both open sessions.
2. [x] **Hook endpoints and registration over HTTP.** `POST /api/projects {repo}` registers or returns an existing project `{id, title}` and never creates `.trail/id` (any local process can reach the port, and a request must not write into an arbitrary directory); a repo without `.trail/id` is refused `not_opted_in`. `.trail/id` is created only by the CLI: `trails serve --repo <path>` as today, and a new `trails register [--repo]` that creates it when absent and then registers over HTTP, for runtimes with no hooks. `GET /api/projects` lists projects. The hook scripts read the project id from `.trail/id` (walking up from the repo) and put `project` in the body of `off-trail`, `edited` and `stop-check`, so the endpoint resolves that project directly; a body with only `runtime_session_id` falls back to the open sessions of every project, most recently started winning, with an in-memory runtime-id cache. The session-start hook registers the repo, then prints `Trails project: <id>` with the runtime id so the agent passes both to `session_start`; the registration is also the liveness probe, one `curl` on the common path, and when nothing answers autostart starts `trails serve --addr <addr>` with no repo (log `~/.trail/server.log`) and registers over HTTP. `serve` without `--repo` no longer defaults to the working directory. `.trail/port` handling is removed from the CLI, hooks, specs, READMEs and tests (`open` and `status` lose their `--repo` flag until step 3); the address is `--addr`, `TRAILS_ADDR` or `127.0.0.1:7777`, and the plugin's `.mcp.json` keeps `${TRAILS_PORT:-7777}` so a machine sets the port once in user settings. The Claude Code mismatch line compares the port of `TRAILS_URL`, the server the hook reached, with `TRAILS_PORT` (7777 when unset) and names `~/.claude/settings.json`; it reads nothing per repo. Spec: adapters.md (endpoints, autostart, the context line, `project` in hook bodies), storage.md (port, `trails register`), trail.md if the session row gains a project column. Verification: `scripts/test-hooks.sh` with a case where two temp repos register against one server and each hook call lands in its own project, one case with no `project` in the body, and one registering a repo with no `.trail/id` that is refused and leaves the directory untouched.
3. [x] **Server routes and CLI.** Every `/api/...` route moves under `/api/p/<id>/...` through one `withProject` wrapper that resolves the id and hands each handler its `*Project` (the `api` struct is built per request from it, not per process); an unknown id is 404. `/api/projects` feeds the list. A page path without the prefix (`/graph`, `/entries/x`) redirects to `/p/<id>/...` when the registry holds one project and to `/` otherwise. `trails open` reads `.trail/id` from the nearest directory at or above the cwd (or `--repo`) and opens `/p/<id>/...`; `trails status` lists every project, or the one `--repo` names. The project `title` is the root sign's title. Spec: web_ui.md (the prefix and the redirect), storage.md (open and status). Verification: `go test ./...` with routes tested under two ids, and `trails open map` from a repo printing a `/p/<id>/` URL.
4. [x] **Frontend and proof.** `/` is the project list (title, entry count, open sessions, open gaps, all from `GET /api/projects`); the router takes `project` as a prefix param, the API client builds URLs from it, the sidebar brand shows the project title and links to `/`. `make proof` captures the project list and one project (`PROJECT` names it, else the first listed). Spec: web_ui.md (project list). Conventions: none declared in this repo. Verification: `npm run build && npm test`, `make proof` green against a server holding two projects.
5. [x] **Verify and release.** `make test`, `make proof`, plugin version 0.5.0, README and adapter READMEs say one server per machine. Verification: `make test` exit 0, proof screenshots read, both of this machine's projects reachable from one process.

## Deviation log

- pre-execution: unknown 1 settled in the plan text (project resolved inside `trail.Record`, not in the SDK's getServer callback) because that callback runs before the body is parsed and the Recorder and Checker were bound to one store.
- pre-execution: step 1 names a `Project` value, a mutex-guarded `Registry` and one resolution point in `trail.Record` (handlers receive `*Project`), and registers nothing per project, because otherwise every tool and route would repeat its own project lookup and dynamic registration would not work.
- pre-execution: step 1 keeps the old `/api` and web routes working on the sole project (409 when ambiguous) and defines `unknown_session` as unlogged, because the plan left the tree uncompilable or untested between steps 1 and 3 and left unlogged-refusal behaviour undefined.
- pre-execution: `POST /api/projects` never creates `.trail/id`; creation moves to the CLI (`trails serve --repo`, new `trails register`) because any local process can reach the port and the original text let a request write into an arbitrary directory, and hookless runtimes still need a way to opt in.
- pre-execution: hook bodies carry `project` read from `.trail/id`, with runtime-id search across projects only as a fallback, because "most recently started open session across projects" makes one repo's hook able to hit another's session and costs a scan per file read.
- pre-execution: two checkouts sharing one `.trail/id` resolve to the later `Open` (log line, `Repo` read at call time) because the `repo` file holds one path per id and clones or worktrees share the id.
- pre-execution: old step 3 split into server routes and CLI (3) and frontend and proof (4); verify and release is step 5, because step 3 changed routes, router, client, shell, CLI and proof at once with no green point between.
- step 1: `trail.Record` takes a generic `trail.Resolver[P]` implemented by `project.Registry`, not the registry itself, because `project` imports `trail` for the sweep and a direct reference would be an import cycle. `Recorder` and `trail.RequireSession` are gone; the resolver replaces both.
- step 1: `serve` with no `--repo` flag still serves the working directory, because the hook autostart passes no other repo until step 2 changes it. `store.ReadID` and `store.EnsureID` split `store.Open`'s id handling so the registry can refuse a repo without an id while `store.Open` stays as it was.
- step 2: the session-start hook probes liveness with `POST /api/projects` instead of `GET /api/map`, because `/api/map` answers 409 once the registry holds two projects and the hook would have started a second server; the probe is the registration, so the common path stays one `curl`. The autostart log is `~/.trail/server.log`, not `server-<id>.log`, because the server no longer belongs to one repo.
- step 2: `GET /api/projects` replies `{projects: [{id, title}]}`; `POST /api/projects` refuses a relative or missing path with 400 and a repo without `.trail/id` with 422 `not_opted_in`. A hook body naming a `project` the server does not hold gets 404 `project_unknown`; an unmatched runtime id still gets the quiet empty reply. The runtime-id cache is asked first and wins while its project holds an open session for the id, so "most recently started wins" applies only on a cache miss.
- step 2: `open` and `status` lose their `--repo` flag (it only named the port file); step 3 gives them one back for `.trail/id`.
- step 3: the coordinator brief called this step "Browser and CLI" and listed the Vue router, API client, graph store, project list and `scripts/proof.mjs`; the plan puts those in step 4, so step 3 changed only the server routes, the CLI, their specs and tests. The embedded front end still calls the unprefixed `/api` routes, which are now 404, so the browser shows no data until step 4 lands.
- step 3: a data route without `/api/p/<id>` is a plain 404, not the step 1 409 `project_ambiguous`, because the sole-project fallback it served is gone with the prefix. `Registry.Sole` stays for `session_start` and the page redirect.
- step 3: `trails open` and `trails status --repo` look for `.trail/id` at or above the directory, as the hook scripts do, not only in it. `status` prints `<title> (<id>): ...` so two projects with the same title stay apart.
- step 3: web_ui.md said the entry page's Supersede button twice; the duplicate sentence is gone.
- step 4: `GET /api/projects` gained `entries`, `open_sessions` and `open_gaps` per project, because the list page needs the counts and one request for all projects beats one `/map` call each. Counts are live (not dormant) entries, sessions with no `ended_at` and open gaps; storage.md says so.
- step 4: storage.md still said the browser routes act on the only open project and answer 409 `project_ambiguous`; step 3 removed that, so the sentence now points at web_ui.md.
- step 4: the project id reaches the API client through a module-level `projectId` ref that the router sets in `afterEach`, not `beforeEach`, because the shell resolved its links against the old route in between and threw "Missing required param". The graph store loads once per project and drops its nodes when the project changes.
- step 4: proof.mjs has no fixture of its own, so the two-project server for the run was seeded by hand (two temp repos with `.trail/map.md`, entries written over MCP) under a temp `--home`.
